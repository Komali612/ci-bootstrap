# How to assemble a workflow from `cookbooks.yaml`

`cookbooks.yaml` (next to this file) is the **single source of truth**, shared
byte-for-byte with the ci-bootstrap service. It contains only what differs per
language. This document is the assembly rule — the fixed scaffolding the service
builds in code (`base.py`) and you build by following the steps here. Both must
produce the same workflow, so **do not improvise structure**: fill the fixed
skeleton below with the cookbook's data and nothing else.

## What's in `cookbooks.yaml`

Two top-level sections:

- `sonar_strategies:` — three reusable Sonar step-lists (`maven`, `dotnet`,
  `generic`). A cookbook names one.
- `cookbooks:` — one entry per build system, keyed by the `build_system` the
  classifier produces. Each has `language`, `setup` (step list), `build` and
  `test` (a string or list of shell lines), `sonar` (a strategy name; default
  `generic`), and `dockerfile`.

## The fixed skeleton

Every generated `ci.yml` is exactly this shape. Only the marked slots come from
the cookbook; everything else is verbatim.

```yaml
# Generated by ci-bootstrap. Review before merging.
name: CI
on:
  push:
    branches:
    - __DEFAULT_BRANCH__
  pull_request:
  workflow_dispatch:
permissions:
  contents: read
  packages: write
jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      # ← 1. cookbook `setup:` steps, verbatim
      # ← 2. Build step
      # ← 3. Test step
      # ← 4. Sonar steps (from the strategy, guard-wrapped)
      # ← 5. Push steps (fixed; Dockerfile from the cookbook)
```

## Assembly steps

**1. Setup** — copy the cookbook's `setup:` steps in order, right after Checkout.

**2. Build** — one step named exactly `Build`. Its `run:` is the cookbook's
`build` value (if it's a list, join the lines; multiple lines → a `run: |` block).

**3. Test** — one step named exactly `Test`, `run:` = the cookbook's `test` value.

**4. Sonar** — take the step-list from `sonar_strategies[<cookbook.sonar>]`
(default `generic`). For **each** step in it, add the **Sonar guard** — the
`if:` and the `env:` below — merging the guard env *before* any `env:` the
strategy step already declares (so e.g. `generic`'s `SONAR_HOST_URL` is kept):

```yaml
    if: ${{ env.SONAR_TOKEN != '' }}
    env:
      SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
      GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

Keep the strategy step's other keys (`name`, `run`/`uses`/`with`) unchanged. The
step names already contain "Sonar" — leave them.

**5. Push** — always these three steps, verbatim except the Dockerfile body.
Omit the first step if the repo already has a `Dockerfile`. Substitute the
cookbook's `dockerfile` where shown:

```yaml
      - name: Write default Dockerfile (Push)
        if: github.event_name == 'push'
        run: |
          cat > Dockerfile <<'DOCKERFILE'
          # ← cookbook `dockerfile:` contents, indented to match
          DOCKERFILE
      - name: Log in to GHCR (Push)
        if: github.event_name == 'push'
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Build and push image (Push)
        if: github.event_name == 'push'
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: __IMAGE__:${{ github.sha }}
```

## Fill the placeholders

The cookbook data (and the Sonar strategies) use three placeholders. Replace
them everywhere before writing the file:

| Placeholder | Replace with | Why |
|---|---|---|
| `__DEFAULT_BRANCH__` | the repo's default branch (e.g. `main`) | scope the push trigger |
| `__SONAR_ORG__` | repo **owner, lowercased** | SonarCloud lowercases GitHub-imported org keys |
| `__SONAR_PROJECT_KEY__` | `<owner>_<name>` (owner's original case) | SonarCloud project-key convention |
| `__IMAGE__` | `ghcr.io/<owner>/<name>`, **both lowercased** | GHCR (like all Docker registries) rejects uppercase image paths; `${{ github.repository }}` would keep the owner's case and fail with "repository name must be lowercase" |

## Why it's shaped this way

- The **Sonar guard** means the scan is skipped (green) until a `SONAR_TOKEN`
  secret exists — a repo without Sonar set up isn't punished.
- The **Push guard** (`github.event_name == 'push'`) means images build only on
  merges to the default branch, never on PRs.
- `permissions: packages: write` is needed for the GHCR push.

## Adding a language

Add one entry under `cookbooks:` in `cookbooks.yaml` (setup, build, test, a
`sonar` strategy name, a dockerfile) and a row to the tables in `SKILL.md`. Only
add a `sonar_strategies:` entry if none of the three existing scanners fit —
which is unusual. Because the service reads the same file, it gains the language
too. (A test in the service repo asserts the skill's copy matches the service's,
so keep them in sync.)
